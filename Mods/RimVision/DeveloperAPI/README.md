# RimVision C# API 1.6

Единое руководство для разработчиков аддонов RimVision. API предоставляет общие точки расширения для интеграции игровых механик, интерфейсов, управления, боевых систем, связанных карт и миниигр. Совместимость оформляется отдельным аддоном-мостом: он связывает контракты RimVision с нативными операциями своего мода.

API находится в `Recovery.Rim3D.dll`. Основное пространство имён –  `Recovery.Rim3D.API`; миниигры находятся в `Recovery.Rim3D`. Текущая версия исходного контракта –  **1.6.0**. API 1.5 был собран и установлен отдельно; изменения 1.6 ещё не собраны и не проверены в игре. Для них выполняется статический разбор. Существующий инструментарий 3D-моделей используется совместно с API.

Контракты не зависят от названий сторонних модов. Подключайте только необходимые провайдеры; остальные механики продолжают работать штатно. Игровые данные, Jobs, резервации, боеприпасы и сохраняемое состояние остаются у их нативного владельца. Наличие API даёт возможность написать интеграцию, но не означает автоматическую совместимость со всеми модами.

API 1.5 расширяет камеру (в том числе третье лицо), анимации пешки/оружия/кистей, элементы HUD, клавиши и раздельные блокировки ввода. Добавлены события представления, отслеживаемые команды, opt-in пассажиры/вертикальное движение и полный цикл удерживаемой атаки. Полные контракты, порядок применения, ограничения и пример –  [камера, анимации, HUD и ввод](PresentationAndInput.md).

API 1.6 добавляет жесты/оси и ввод управления, жизненный цикл камеры и видов, отслеживание фактических Jobs, взаимодействия, модели, анимационные события, эффекты, диагностику и проверку контрактов. Контракты и opt-in пример –  [расширения API 1.6](AdvancedExtensions.md).

## Подключение аддона

Целевая платформа –  .NET Framework 4.7.2. Добавьте ссылки на `Recovery.Rim3D.dll`, `Assembly-CSharp.dll` и необходимые `UnityEngine*.dll` из установленной игры. Не включайте копии этих DLL в свой аддон: для ссылок используйте `Private=false`.

Укажите зависимость `papaya.rimvision` и загрузку после RimVision в `About/About.xml`. Если аддон использует классы другого мода, объявите также его зависимость. Для необязательной совместимости проверяйте `ModsConfig.IsActive(packageId)` перед регистрацией; код со ссылками на отсутствующую DLL должен находиться в отдельно загружаемой интеграции либо использовать reflection.

Регистрируйте расширения один раз в `LongEventHandler.ExecuteWhenFinished`, после загрузки Def. Все вызовы API выполняются в основном потоке. `RimVisionApi.Version` возвращает версию публичного контракта. Аддон для этого API требует соответствующую DLL RimVision: проверка свойства Version сама по себе не обеспечивает загрузку на старой DLL, в которой используемого типа API ещё нет.

Пример проекта находится в `Example/`. Он добавляет действие ремонта в меню FPV, надпись HUD и миниигру ремонта. Измените имена, packageId и идентификаторы регистраций перед использованием. Для сборки примера из его каталога:

```powershell
dotnet build RimVision.ApiExample.csproj -c Release -p:GameRoot="D:/Games/RimWorld" -p:RimVisionRoot="D:/Games/RimWorld/Mods/RimVision"
```

Скопируйте `About/` и полученную `Assemblies/` в отдельную папку аддона. Это пример исходного кода; его сборка и запуск в рамках разработки API не выполнялись.

## Идентификаторы, порядок и отключение

Регистрации `RimVisionApi`, `RimVisionSpatial`, `RimVisionControl`, `RimVisionPresentation` и `RimVisionCombat` принимают уникальный ID вида `author.mod:feature` длиной до 160 символов и возвращают `IDisposable`. Повторный ID в том же реестре вызывает исключение. Одинаковый ID в разных реестрах допустим. Порядок: больший `priority` раньше, при равенстве –  ID по ordinal-сравнению. Для провайдеров выбирается первый подходящий обработчик (у presentation –  отдельно по Channels); новые camera/presentation modifiers последовательно применяются после него, а HUD провайдеры совместно уточняют разметку; действия имеют отдельные ID, расширения вида создаются в указанном порядке. Обычные API-действия добавляются после штатных пунктов меню; межкарточные требуют собственного интерфейса. У миниигр отдельные правила регистрации по JobDef/категории, описанные ниже.

Храните возвращённый handle, если нужно снять регистрацию; сборщик мусора сам регистрацию не отменяет. `Dispose` handle можно вызывать повторно. Регистрации обычно живут всё время работы игры. Не меняйте регистрации игровых действий или миниигр во время Multiplayer-сессии: их состав должен совпадать у участников.

Расширения сцены создаются при Build локального 3D-вида. Регистрация нового расширения применяется при следующем открытии/пересоздании вида. После снятия регистрации существующий экземпляр очищается при следующем обращении к сессии либо при закрытии вида. При переходе на другую карту старые экземпляры освобождаются, новые создаются для новой карты.

## Жизненный цикл расширения

```csharp
RimVisionApi.RegisterExtension("author.mod:overlay", () => new MyOverlay());

public sealed class MyOverlay : RimVisionExtension
{
    public override void DrawHud(RimVisionView view, Rect viewport)
    {
        var state = view.State;
        if (state.Pawn == null) return;
        Widgets.Label(new Rect(viewport.x + 20, viewport.y + 100, 260, 30), state.Pawn.LabelShort);
    }
}
```

Фабрика должна каждый раз возвращать новый экземпляр. В примере нужны `using Recovery.Rim3D.API;`, `using UnityEngine;`, `using Verse;`.

Последовательность:

1. `Open(view)` –  геометрия и камера уже подготовлены; начальная FPV-пешка ещё может не быть выбрана.
2. `StateChanged(view, previous)` –  при смене Map, пешки, FirstPerson, CanControl или MortarAiming. Текущее состояние читается через `view.State`; промежуточные переходы между обновлениями не накапливаются.
3. `Update(view)` –  обновление локального расширения после штатной камеры и миниигры, без GUI.
4. `BeforeRender(view)` –  перед фактическим рендером камеры, включая прогрев. Обновляйте здесь свои визуальные объекты, без изменений симуляции.
5. `DrawHud(view, viewport)` –  Unity IMGUI в координатах viewport. Вызывается для GUI-событий, а не только Repaint. В режиме скриншотов, при падении и наведении миномёта этот HUD скрыт вместе с обычным HUD.
6. `Dispose()` –  перед уничтожением ресурсов сцены, в обратном порядке расширений. Отпишите внешние события и освободите собственные ресурсы, которыми API не владеет.

Исключение в локальном callback записывается в журнал и отключает этот экземпляр до пересоздания вида; остальные расширения продолжают работу. API сохраняет игровой RNG вокруг локальных callback. Для анимаций и миниигр используйте собственный `System.Random`, время Unity и локальные поля. В callback нельзя изменять мир, создавать Job или выдавать награды; для пользовательской команды вызывайте `RequestAction`.

`RimVisionApi.Current` возвращает nullable-снимок открытого вида, либо `null`, если окна нет. `RimVisionView.State` читает актуальное состояние, включая FPV, управляемую пешку, цель/клетку наведения, InputBlocked, позицию и поворот камеры. После закрытия `view.IsOpen == false`, а чтение State вызывает ObjectDisposedException. Не храните снимки как источник игрового состояния.

`BlockInput()` блокирует все каналы; перегрузка `BlockInput(RimVisionInputChannels)` позволяет независимо блокировать движение, обзор, бой, взаимодействие и shortcuts. Метод возвращает отдельный handle: держите его только пока ваш интерфейс должен блокировать управление и освободите при закрытии. Несколько блокировок независимы; закрытие расширения снимает их влияние. Для обычного окна RimWorld предпочитайте штатные `Window.preventCameraMotion` и `forcePause`.

`FocusCell` работает только в обзорном режиме и запускает существующий перелёт камеры. `TryProject` принимает позицию в координатах карты, возвращает GUI-координаты и `false` для точки за камерой или вне viewport; туман войны и видимость объекта проверяйте отдельно.

`RefreshPawn` и `RefreshThing` запрашивают обновление штатных визуальных кэшей после изменения внешности/состояния другим модом. Они не изменяют симуляцию. Вызывайте по событию изменения, а не каждый кадр. В текущей версии принимаются только заспавненные объекты текущей карты.

## Состояние вида и методы RimVisionView

`RimVisionApi.Current` читает состояние активного вида без создания расширения. Внутри расширения используйте переданный `RimVisionView`, чтобы работать именно со своей сессией. Снимок `RimVisionViewState` содержит:

| Поле | Значение |
| --- | --- |
| `Map` | Активная карта вида. |
| `Pawn` | Управляемая/наблюдаемая пешка; может быть null. |
| `FirstPerson` | Включён ли FPV-режим вида. |
| `CanControl` | Доступно ли игровое управление пешкой. |
| `InputBlocked` | Состояние блокировки управления/интерфейса на момент чтения. |
| `MortarAiming` | Активен ли специальный режим наведения орудия. |
| `Multiplayer` | Активна ли Multiplayer-сессия. |
| `AimedThing`, `AimedCell` | Текущие объект и клетка обычного наведения. |
| `CameraPosition`, `CameraRotation` | Локальная поза камеры в координатах активной карты. |

API 1.5 также предоставляет Weapon/HeldItem, AimBlend/Recoil, Stamina, Sprinting/Sneaking/Moving, Acting/Resting/NativeControl, LastMeleeAttackTick, BlockedInput, параметры проекции, фактическую видимость тела/FPV-предметов, MovementYaw и AimRay. FirstPerson по-прежнему обозначает режим управления пешкой, включая стороннюю камеру третьего лица. Полные значения и события описаны в [дополнении 1.5](PresentationAndInput.md).

Это локальный снимок представления, а не авторитетный контекст игровой команды. Изменение цели/блокировки между двумя чтениями допустимо. StateChanged сообщает только о смене Map, Pawn, FirstPerson, CanControl или MortarAiming; для остальных значений читайте State при обновлении.

| Метод/свойство RimVisionView | Назначение |
| --- | --- |
| `IsOpen`, `State` | Проверка срока жизни и чтение текущего состояния. |
| `RequestAction(id, target, cell, value = 0)` | Запрос зарегистрированного действия активной карты. |
| `RequestLayerAction(id, targetMap, target, cell, value = 0)` | Запрос действия связанной карты. |
| `RefreshPawn(pawn)` | Обновление представления заспавненной пешки активной карты. |
| `RefreshThing(thing)` | Обновление представления заспавненного объекта активной карты. |
| `FocusCell(cell)` | Перелёт обзорной камеры к клетке; в FPV возвращает false. |
| `TryProject(mapPosition, viewport, out position)` | Проекция координат активной карты в GUI. |
| `TryProject(map, mapPosition, viewport, out position)` | Проекция координат отображаемой связанной карты в GUI. |
| `LayerOffset(map)` | Высота отображаемой карты относительно активной, либо null. |
| `PrepareLayer(map)` | Запрос приоритетной локальной подготовки уже загруженной связанной карты; true означает готовую сцену. Не генерирует Map и не назначает переход. |
| `TryPick(ray, maximumDistance, out hit)` | Выбор ближайшей поверхности/цели среди отображаемых карт. |
| `CreateSceneObject(name)` | Создание принадлежащего расширению объекта активного вида. |
| `CreateLayerObject(map, name)` | Создание объекта в проходе указанной отображаемой карты. |
| `OwnResource<T>(resource)` | Передача расширению владения новым Mesh, Material или Texture; возвращает переданный объект. |
| `BlockInput()` | Независимая блокировка ввода с handle IDisposable. |

Статический `RimVisionApi.RequestAction` эквивалентен запросу обычного действия для текущего активного вида; при отсутствии подходящего вида возвращает false. Статический `RimVisionSpatial.RequestAction` делает то же для действия связанной карты.

## Визуальные ресурсы

`CreateSceneObject(name)` создаёт объект на слое 3D-вида, под отдельным корнем расширения. Используйте localPosition в координатах карты: общий перенос сцены API учитывает сам. Создаваемые вручную дочерние объекты должны получать тот же Unity layer, поскольку он не наследуется автоматически.

Объекты этого поддерева удаляются при закрытии/ошибке расширения. В API 1.3 `view.CreateSurfaceMaterial(texture, color)` создаёт уже принадлежащий расширению материал с тем же освещением и camera-relative проекцией, что и мир RimVision; текстура остаётся заимствованной. Не оборачивайте результат повторным владением у другого расширения. Для произвольных ресурсов передавайте `OwnResource(new Material(...))`, `OwnResource(new Mesh())` или собственную текстуру, чтобы API освободил их после Dispose расширения. RenderTexture предварительно получает Release. Не передавайте заимствованные текстуры, материалы игры, AssetBundle-ресурсы или ресурс, уже принадлежащий другому владельцу. Зарегистрированный ресурс не уничтожайте повторно самостоятельно. Уничтожение GameObject не освобождает созданные отдельно Mesh/Material/Texture.

Эти расширения никогда не создаются для simulation-only MapView на удалённых клиентах. Состояние расширений локальное, автоматически не сохраняется; для постоянных данных используйте собственные ModSettings/GameComponent и штатный Scribe.

## Действия и совместимости

### Сигнатуры регистраций действий

```csharp
IDisposable RimVisionApi.RegisterExtension(
    string id, Func<RimVisionExtension> create, int priority = 0);

IDisposable RimVisionApi.RegisterAction(
    string id,
    Func<RimVisionActionContext, string> label,
    Func<RimVisionActionContext, bool> visible,
    Func<RimVisionActionContext, AcceptanceReport> validate,
    Func<RimVisionActionContext, bool> execute,
    int priority = 0);

IDisposable RimVisionApi.RegisterJobAction(
    string id,
    Func<RimVisionActionContext, string> label,
    Func<RimVisionActionContext, bool> visible,
    Func<RimVisionActionContext, AcceptanceReport> validate,
    Func<RimVisionActionContext, Job> createJob,
    int priority = 0);
```

В блоках сигнатур имя типа перед методом показывает точку входа; это справочная запись, а не готовое объявление класса. В своём коде передавайте реальные delegates/экземпляры провайдеров. Основные using: `System`, `UnityEngine`, `Verse`, `Verse.AI`, `Recovery.Rim3D.API`; для миниигр также `Recovery.Rim3D`.

`RegisterJobAction(id, label, visible, validate, createJob, priority)` добавляет пункт меню и фабрику штатного Job. Создание и назначение Job происходят только при выполнении команды. Назначение проходит через `PawnControl.OrderAction`: сохраняются резервации и возврат к ручному управлению.

`RegisterAction(id, label, visible, validate, execute, priority)` подходит для способности, переключателя или другой штатной операции, которой не нужен Job. `execute` возвращает true только после успешного действия. Нельзя повторно применять уже выполненную операцию и возвращать false.

Контекст содержит `Map`, `Pawn`, `Target`, `Cell` и целочисленный `Value`. В меню Value равен нулю; из своего интерфейса можно передать параметр:

```csharp
view.RequestAction("author.mod:ability", target, target.Position, value: 2);
```

`label` возвращает текст, `visible` определяет наличие строки, `validate` возвращает `AcceptanceReport` с причиной запрета. Они должны быть чистыми: без RNG, создания Job и изменения мира. Validate вызывается и при запросе, и при исполнении; Visible используется только локальным меню. Не используйте настройки локального интерфейса внутри Validate/Execute.

Ядро проверяет активное управление пешкой, принадлежность карты, существование цели и туман войны. Target должен быть заспавнен на этой карте; для действия без объекта передайте null. Cell может быть `IntVec3.Invalid`, иначе требуется открытая клетка этой карты. Дальность, владение объектом, доступность способности, стоимость, запреты, ограничения Value и другие правила своего действия проверяет ваш Validate. Для Job дополнительно проверяются штатные резервации при назначении. Используйте нативные механизмы целевого мода и его WorkGiver/JobDriver.

Возврат true из RequestAction означает принятие запроса, а не гарантированное завершение операции. В одиночной игре запрос выполняется после локальных callback ближайшего WindowUpdate; при смене управляемой пешки до исполнения запрос отбрасывается. Это отделяет игровые мутации от GUI/рендера и восстановления RNG. В Multiplayer запрос отправляется через существующие Work-команды RimVision с namespaced Kind; формат пакета не расширен. При исполнении снова проверяются сессия владельца, активная пешка и Validate. Фабрика Job/Execute работает на синхронизированной стороне.

Исключения игрового Validate/Execute не маскируются: обработчик обязан корректно работать на всех клиентах. Параметры дополнительного сетевого payload не предусмотрены; доступны стабильный ID, Thing, Cell и int Value. Для более сложных действий используйте детерминированные игровые данные или собственный согласованный протокол целевого мода.

## Нативное управление

Регистрация: `RimVisionControl.RegisterProvider(string id, RimVisionControlProvider provider, int priority = 0)` возвращает IDisposable. Реализуйте наследника провайдера:

| Метод | Контракт |
| --- | --- |
| `Handles(Pawn actor)` | Чистый выбор поддерживаемой пешки/механики. |
| `Carrier(Pawn actor)` | Нативный объект, определяющий перемещение; допустима сама Actor. |
| `CanControl(RimVisionControlContext context)` | Чистая проверка доступности, возвращает AcceptanceReport. |
| `Position(RimVisionControlContext context)` | Чистая авторитетная позиция; по умолчанию центр клетки Carrier. |
| `Attached(context, RimVisionControlChange reason)` | Начало привязки; по умолчанию без действий. |
| `Detached(context, RimVisionControlChange reason)` | Завершение привязки; по умолчанию без действий. |
| `Move(context, RimVisionMovementInput input)` | Исполнение нативного движения. |
| `Cancel(context)` | Исполнение запроса отмены; по умолчанию без действий. |
| `SetCombat(context, bool enabled)` | Исполнение смены боевого режима; по умолчанию false. |
| `OrderJob(context, Job job)` | Передача Job нативному владельцу; по умолчанию false. |

Handles, Carrier, CanControl и Move обязательны к реализации. Другие методы виртуальные. Провайдер выбирается независимо от открытого локального 3D-окна и должен регистрироваться также на клиентах, где используется только симуляция.

`RimVisionControlContext` предоставляет `Actor`, `Carrier`, `Map`, `Multiplayer`. Actor сохраняет роль действующего лица, Carrier определяет нативное перемещение. `RimVisionControl.TryGetContext(Pawn actor, out RimVisionControlContext context)` читает текущую подходящую связь: true означает действительные spawned Actor/Carrier на одной карте, но не принятие CanControl и не захват управления.

`PawnControl.HasNativeControl` сообщает о выбранном провайдере, включая временно недоступную или некорректную связь; это не признак успешного движения. `PawnControl.Active` остаётся проверкой возможности управления.

`RimVisionMovementInput` содержит:

| Поле | Значение |
| --- | --- |
| `Input` | Vector2 локального ввода, длина ограничена единицей; аналоговая величина сохраняется. |
| `Direction` | Vector3 направления в координатах карты после применения Yaw; Y=0. |
| `Yaw` | Угол ввода в градусах. |
| `DeltaSeconds` | Шаг обработки в диапазоне 0–0.1 секунды. |
| `Tick` | Текущий Find.TickManager.TicksGame при создании ввода. |
| `Sneaking`, `Sprinting` | Запрошенные состояния движения; ограничения и фактический расход определяет мост. |

`Handles(actor)` читает реальную связь целевого мода; `Carrier(actor)` возвращает её носителя. Разрешён `Carrier == Actor`. По умолчанию действующее лицо остаётся spawned управляемым колонистом игрока, а носитель spawned на той же карте. API 1.5 позволяет провайдеру явно включить SupportsContainedActor: тогда проверяется настоящая цепочка ParentHolder до носителя. Ограничения пеших взаимодействий и Multiplayer описаны в [дополнении 1.5](PresentationAndInput.md#нативное-движение-и-пассажиры). Носитель может быть любым Thing, но право управлять им проверяет мост.

`CanControl(context)` возвращает AcceptanceReport. Он обязан проверить текущую связь, право управления, доступность/состояние носителя и ограничения целевого мода. Наличие провайдера разрешает сохранить его неinterruptible Job, но не отменяет смерть, downed, mental state и стандартные ограничения принадлежности действующего лица. При отказе ручное перемещение блокируется.

Handles, Carrier, CanControl и Position –  чистые запросы. Они могут вызываться из UI, Harmony и симуляции несколько раз за кадр/тик; не создавайте в них Jobs/ресурсы и не меняйте мир или собственное игровое состояние. Rand восстанавливается после запроса. Игровые изменения выполняйте только в авторитетных Move/OrderJob/Cancel/SetCombat/Attached/Detached либо registered actions.

`Position(context)` возвращает авторитетную позицию в координатах карты. По умолчанию это клетка Carrier; старый XZ-контракт сохраняется и Y отбрасывается. При SupportsVerticalMovement=true API 1.5 сохраняет Y и передаёт трёхмерный ввод. Для непрерывного движения возвращайте позицию из нативного состояния целевого мода. Этот запрос не должен читать DrawPos, tweener, Unity Time или локальную интерполяцию. Рендерная высота задаётся отдельно.

`Move(context, input)` исполняется только в SP либо внутри MP simulation. Input содержит нормализованный по длине ввод, направление в координатах карты, yaw, sneak/sprint, DeltaSeconds и текущий TicksGame. Нулевой ввод тоже доставляется: мост должен уметь остановить/обновить нативное движение. Пауза и нулевой delta не вызывают Move. В SP delta зависит от кадров, в MP это штатный шаг контроллера 1/60 секунды. Синхронный input-пакет с delta=0 движение не продвигает.

Мост вызывает существующие операции движения/Jobs целевого мода и проверяет его размеры, коллизии, двери, путь, выносливость, скорость и эффекты движения. RimVision не перемещает Actor/Carrier, не тратит пешую выносливость и не подменяет их нативные path followers. Пространственные CanStand/переходы не применяются автоматически к носителю: согласование этих двух мостов принадлежит адаптеру. Вызов Move не создаёт Job автоматически.

`OrderJob(context, job)` получает Job из существующей синхронизированной границы. По умолчанию отказывает. При `true` мост принимает владение Job и сам проводит штатные проверки/reservations/StartJob; при `false` не меняет мир, не возвращает Job в pool и не сохраняет его: RimVision возвращает его в pool. Если callback бросает исключение после передачи Job нативному API, RimVision не возвращает потенциально активный Job в pool; cleanup частично выполненной операции принадлежит мосту.

`Cancel` обрабатывает запрос отмены без принудительной остановки/замены Job со стороны RimVision. `SetCombat` по умолчанию отказывает; мост должен безопасно изменить режим через целевой мод и вернуть результат. Обычный ручной сон требует сначала завершить нативное управление/спешиться. Остальные registered actions продолжают проходить штатную границу валидации и могут запрашивать посадку, высадку, смену седла и способности через нативный API.

## Жизненный цикл нативного управления

`Attached` и `Detached` вызываются только авторитетным PawnControl, никогда локальной MP-копией или рендерером слоя. Причины: Acquired, Changed, Restored, Unavailable, Released. Смена provider/carrier/map завершает старую привязку и создаёт новую на следующей границе управления. Attached уведомляет о передаче ответственности, в том числе когда CanControl временно запрещает ввод; это не команда автоматической посадки.

При передаче удаляется только отложенный возвратный Job RimVision, снимаются его старые manual-action bookkeeping; при выходе из пешего режима восстанавливается исходный FireAtWill. Нативные текущий Job, остальные queued Jobs, reservations и связь всадника не очищаются. При выходе из 3D сохранённые до пешего управления задания добавляются в конец нативной очереди; drafted/fire-at-will принудительно не восстанавливаются. Мост сам решает, должна ли пешка спешиться при Released. Detached может получить уже удалённого/перемещённого носителя –  проверяйте ссылки.

Мост не должен вызывать Acquire/Dispose/OrderAction/ReturnToManual контроллера рекурсивно из lifecycle callback. Вызывайте нативный API целевого мода. Его компоненты остаются единственным владельцем сохраняемых связи всадник–носитель, экипировки, скорости и Jobs. Новых Scribe-ключей привязки у RimVision нет. После загрузки она заново определяется по Handles/Carrier и получает Restored. После ошибки управляющего callback движение остаётся заблокированным до смены привязки/повторного захвата; исключения логируются.

## Поза, видимость и камера

Регистрация: `RimVisionPresentation.RegisterProvider(string id, RimVisionPresentationProvider provider, int priority = 0)` возвращает IDisposable.

| Метод | Контракт |
| --- | --- |
| `Handles(Pawn pawn)` | Обязательный чистый выбор пешки для визуального провайдера. |
| `DrawPawn(Pawn pawn, Pawn observer, bool defaultVisible)` | Итоговая локальная видимость внутри обязательных ограничений карты; по умолчанию defaultVisible. |
| `PawnPose(Pawn pawn, ref RimVisionPose pose)` | Изменение вычисленной позы пешки; по умолчанию без изменений. |
| `CameraPose(Pawn actor, ref RimVisionPose pose)` | Изменение вычисленной FPV-позы; по умолчанию без изменений. |

`new RimVisionPose(Vector3 position, Quaternion rotation)` создаёт позу с изменяемыми свойствами `Position` и `Rotation`. У принятой позы координаты и quaternion должны быть конечными, quaternion –  ненулевым; поворот нормализуется перед применением. Изменение позы не меняет размер/масштаб объекта.

`PawnPose` получает уже вычисленную позу модели/спрайта и может заменить Position/Rotation. `CameraPose` получает FPV-позу после высоты опоры, bob и позы сна, до общего camera flight. Координаты относятся к собственной карте, без смещения отображаемого этажа. Для седла прибавляйте его высоту к текущей позе; для сложной геометрии берите seat/socket из нативной модели. Эти callbacks не запускаются для corpse; камера падения и миномёта сохраняет свой режим.

`DrawPawn(pawn, observer, defaultVisible)` позволяет скрыть носителя либо показать тело всадника в FPV. Observer –  управляемая пешка этого вида или null. Ограничения spawned/map/fog/spatial DrawThing остаются обязательными. Скрытие модели является только визуальным: оно не меняет физические попадания или игровую доступность цели. Поза не меняет hitbox ванильного боя, а текущий 3D-пикер использует положение существующей карточки/модели.

Эти callbacks локальные, только читают мир; Rand восстанавливается после вызова. Невалидная поза/исключение оставляет стандартную позу. Владение Unity-ресурсами не передаётся провайдерам: дополнительные модели и эффекты создавайте через прежний RimVisionExtension/RimVisionView и инструментарий моделей.

## Нативный бой

Регистрация: `RimVisionCombat.RegisterProvider(string id, RimVisionCombatProvider provider, int priority = 0)` возвращает IDisposable. Все три метода наследника обязательны:

| Метод | Контракт |
| --- | --- |
| `Handles(Pawn actor, RimVisionAttackKind kind)` | Чистый выбор обработчика Ranged либо Melee. |
| `Validate(RimVisionCombatContext context)` | Чистая повторяемая проверка, возвращает AcceptanceReport. |
| `Execute(RimVisionCombatContext context)` | Исполнение нативной атаки; bool подтверждает успех. |

`RimVisionCombatContext` предоставляет `Actor`, `Carrier`, `Map`, `Kind`, `Target`, `Cell`, `Origin`, `Direction`, `Mode`, `Begin`, `Tick`. Carrier берётся из действительной связи управления, иначе равен Actor. Tick читает текущий TicksGame при обращении. Для Melee передаются позиция контроллера, нулевое Direction, Mode=0 и Begin=true. Контекст не предоставляет локальный MapView, GUI или ссылку на Unity-камеру.

Handles и Validate могут вызываться вне исполнения и не должны менять мир; Rand вокруг них восстанавливается. Исключение в выборе, Validate или Execute записывается в журнал и отклоняет эту атаку. Следующий провайдер или стандартная атака после этого не запускаются. При частично выполненном Execute возвращение false не откатывает мир: обработчик обязан сам соблюдать целостность нативной операции.

`Handles(actor, kind)` отдельно выбирает Ranged/Melee. `Validate(context)` только читает состояние. `Execute(context)` вызывается после повторной проверки внутри SP/синхронного исполнения; возвращает успех. После выбора провайдера стандартная FPV-атака не выполняется, даже при отказе/ошибке: двойных снарядов и урона быть не должно. Нативные ranged verbs выбранного боевого провайдера больше не сбрасываются пешим MaintainControl.

Для Ranged сохраняются Active, Drafted, Shooting skill/Violent, пауза и проверки конечности ray. Для Melee сохраняются skill/Violent, пауза, действительная живая цель, карта и правило подтверждения атаки дружественной цели. Мост получает Actor, Carrier, Map, Kind, Target, Cell, Origin/Direction, Mode/Begin, Tick. Ranged Target содержит выбранную Pawn либо null; для остальных целей используйте Cell или отдельное registered action. Melee Target содержит штатную выбранную Thing.

Мост обязан проверить нативную доступность оружия/способности, cooldown/warmup, допустимость текущего Job, дистанцию, LOS, цель, боеприпасы, разрешённую точку выстрела относительно текущего носителя и правила mounted combat. В MP камера не является доверенным источником координат выстрела: проверяйте Origin/Direction относительно нативного seat/muzzle на стороне исполнения. Штатный лимит высоты пешего FPV не применяется к нативному боевому провайдеру –  допустимую геометрию задаёт его Validate.

При UsesInputPhases=false ЛКМ направляет выбранному Ranged-провайдеру одно нажатие через прежнюю Fire-команду (Mode=0, Begin=true); прежняя пешая очередь burst/auto отключается и не дублирует нативную. Очередь, длительность серии, расход и завершение огня принадлежат нативному Verb/Job/компоненту. API 1.5 добавляет opt-in UsesInputPhases с ValidateInput/Input и отдельным синхронизированным протоколом Pressed/Held/Released/Cancelled; прежний поток Execute не меняется. Для произвольных дополнительных команд также доступны registered actions с value. Melee использует прежнюю команду Melee. Старые сетевые пакеты и Scribe-ключи не меняются.

## Пространственный провайдер

Пространственный API описывает группу уже существующих связанных карт и их локальное 3D-представление. Он подходит для дополнительных областей мира, вертикальных слоёв и переходов между ними; данные связей остаются у целевого мода.

Результаты и контексты:

| Тип | Состав |
| --- | --- |
| `RimVisionTraversalContext` | `Pawn`, исходная `Map`, непрерывная `Position`, `Direction`. |
| `RimVisionTraversal` | `Destination`, `Exit`, целочисленный `Route`; публичный конструктор `(Map destination, IntVec3 exit, int route = 0)`. |
| `RimVisionSpatialHit` | `Map`, nullable `Thing`, `Cell`, `Point`, `Distance`. |
| `RimVisionLayerActionContext` | `Pawn`, `SourceMap`, `TargetMap`, `Target`, `Cell`, `Value`. |

`PawnControl.CollisionRadius` предоставляет радиус тела стандартного ручного движения для проверки края/прохода. Провайдер нативного управления определяет геометрию и коллизии носителя самостоятельно.

Создайте наследника `Recovery.Rim3D.API.RimVisionSpatialProvider` и один раз зарегистрируйте его через:

```csharp
IDisposable registration = RimVisionSpatial.RegisterProvider("author.mod:topology", provider);
```

Провайдер регистрируется на всех клиентах, независимо от того, открыто ли у них 3D. Он не должен создавать сцену, генерировать карты или хранить локальное состояние камеры. Получайте карты/этажи из сохраняемых данных целевого мода; не создавайте параллельный реестр этажей. Приоритет и конфликты ID работают так же, как у остальных регистраций. Для карты выбирается первый подходящий провайдер в порядке priority/ordinal ID; одна группа этажей должна обслуживаться одним экземпляром провайдера.

| Метод | Назначение |
| --- | --- |
| `Handles(Map)` | Принадлежит ли карта поддерживаемой группе этажей. |
| `Elevation(Map)` | Абсолютная высота основания этажа в общем пространстве группы, в клетках RimWorld. |
| `CollectLayers(Map, List<Map>)` | Добавить ближайшие существующие карты для совместного отображения (до 16 дополнительных). |
| `CollectMaps(Map, List<Map>)` | Полная нативная группа для проверки связей, выбора пешек и симуляции пуль; по умолчанию вызывает CollectLayers. |

Handles, Elevation и CollectLayers обязательны к реализации. У виртуальных методов значения по умолчанию: Revision=0, DrawFloor/DrawRoof/DrawThing/CanStand=true, SurfaceHeight=0, IsTraversalJob/TryGetTraversal/ValidateTraversal/CanInteract=false, CreateTraversalJob=null. Revision изменяйте для всей группы карт при изменении общих правил.

CollectLayers может включать активную карту и повторяющиеся записи –  ядро их не дублирует. Используются только уже загруженные `Current.Game.Maps`; провайдер назначения должен совпадать с провайдером исходной карты. Максимум –  16 дополнительных отображаемых карт; выбирайте ближайшие/нужные этажи в самом провайдере. Сам факт отображения не разрешает взаимодействия.

Этажи совмещаются по X/Z; текущий контракт поддерживает вертикальное смещение без поворота, горизонтального сдвига и масштаба. Разные точки входа/выхода задаются нативным переходом, а не растягиванием карт. Высоты должны быть конечными. Удобный шаг типового перекрытия –  около 2.12 клетки, но фактические размеры определяет аддон и его модели.

Изменение Revision ставит геометрию активного и связанных этажей в прежнюю очередь обновления чанков; это не мгновенная полная пересборка. Обычные изменения вещей, крыш, земли и пешек также приходят через существующие события карты. Удалённая карта освобождается при следующем обновлении вида. Регистрацию провайдера можно снять: основной вид вернётся к обычной геометрии, а дополнительные сцены будут освобождены. Состав игровых провайдеров нельзя менять локально во время Multiplayer.

## Отображение связанных карт

RimVision создаёт для дополнительных карт визуальные контексты существующего рендера: штатные 3D-модели, стены, земля, мебель, двери, пешки и визуальные обновления. Они не выполняют тики карты, не управляют пешкой, не захватывают мышь, не создают AudioListener и не запускают локальные расширения/HUD/миниигры повторно. Небо, погода, слушатель и ввод принадлежат активному виду.

Карты рисуются отдельными проходами в общий RenderTexture с сохранением глубины. Каждый проход использует освещение, крыши, снег и высоту своей карты. Отображение нескольких карт не объединяет их симуляцию и не создаёт второй экземпляр мира.

Пол и потолок вырезаются независимо. Для лестничного проёма обычно нужно отключить крышу внизу и пол наверху в соответствующих клетках. Модель лестницы и боковые грани проёма предоставляет существующий инструментарий моделей либо собственный объект расширения. Скрытие пола не создаёт автоматически физическую опору, падение или отверстие в стене.

DrawFloor/DrawRoof должны учитывать реальные данные и туман войны. Не используйте визуальную прозрачность в качестве разрешения действия. Пикер учитывает туман каждой карты; этот визуальный запрос не является проверкой игровой линии видимости.

## Высота опоры и нативные переходы

SurfaceHeight получает положение X/Z на текущей карте и возвращает высоту опоры относительно этой карты. Высота прибавляется к штатному FPV-положению камеры и к представлению пешки, сохраняя обычные высоту глаз и эффекты камеры. Игровой `Pawn.Position` и внутренний `PawnControl.Position` остаются координатами карты; дополнительная игровая Y-координата не сохраняется и не передаётся в пакете ввода.

Пример расчёта для прямого подъёма вдоль Z:

```csharp
float progress = Mathf.Clamp01((position.z - stairStartZ) / stairLength);
return progress * (Elevation(upperMap) - Elevation(lowerMap));
```

Проверяйте, находится ли пешка на нужной лестнице. На верхней карте обратный участок должен возвращать высоту относительно её основания. Для непрерывности в точке смены карты должно выполняться:

`Elevation(source) + SurfaceHeightBefore == Elevation(destination) + SurfaceHeightAfter`.

После штатного перехода в пределах группы ядро активирует подготовленную сцену карты назначения и сохраняет прежнюю сцену как дополнительный слой, не пересобирая геометрию всех этажей. При первом открытии 3D уже загруженные слои (до 16 дополнительных) подготавливаются под начальным экраном загрузки и прогреваются первым рендером. Новые слои готовятся по кадрам в основном потоке; незавершённая сцена не выдаётся через LayerOffset. Расширение может заранее повысить приоритет назначения через PrepareLayer. PawnControl и RenderTexture передаются новому активному виду. Генерация новых игровых Map остаётся нативной операцией целевого мода; фоновых вызовов Unity/Map нет. Отдельный чанк всё ещё может превысить целевой бюджет; кадровые задержки без игрового замера не гарантируются.

По умолчанию расширения закрываются и открываются заново при смене активной карты. В API 1.4 расширение может переопределить `RetainOnMapTransfer => true`: экземпляр, RimVisionView и принадлежащие ему ресурсы сохраняются внутри той же пространственной группы. Делегаты и камера переключаются на новую активную сцену; следующий Update сообщает StateChanged с предыдущей Map. CreateSceneObject остаётся в локальных координатах активной карты, CreateLayerObject остаётся привязан к указанной карте. Не сохраняйте нативную Map/пешку как неизменный контекст. При удалении слоя его GameObject исчезает независимо от сессии: отдельно принадлежащие расширению Mesh/Material/Texture всё равно требуют своего cleanup. Выход из группы, закрытие окна и ошибка callback завершают обычный Dispose.

`RimVisionPresentation.TickFraction(map)` возвращает локальную долю следующего тика от 0 до 1, учитывает скорость и паузу карты в SP/Multiplayer. Используйте только для визуальной интерполяции PawnPose, CameraPose и моделей. SurfaceHeight, валидация, урон и остальные вычисления симуляции должны читать нативное тиковое состояние без этой доли.

CanStand –  дополнительное ограничение к существующей проверке прохода RimWorld и коллизии тела. Оно не разрешает проход сквозь штатные стены. Учитывайте `PawnControl.CollisionRadius` при проверке краёв проёма; запретите шаг за край без лестницы. Общей физики падения между этажами и универсального вертикального rigidbody в API нет. Переход через непроходимую клетку должен выполнять допустимый нативный Job лестницы/лифта.

TryGetTraversal вызывается только при попытке движения активной пешки без другого выполняемого действия, после проверки паузы и занятости. Контекст содержит Pawn, исходную Map, непрерывную Position и нормализованное направление. Возвращаемый `RimVisionTraversal` содержит Destination, Exit и целочисленный Route. Выбор маршрута должен опираться на игровые координаты и нативные связи лестниц, не на камеру или Time.

Ядро проверяет наличие связанной карты и допустимость Exit, вызывает ValidateTraversal, затем CreateTraversalJob и штатный `PawnControl.OrderAction`. Job обязан распознаваться IsTraversalJob. Он сохраняет нативные резервации, движение, перенос пешки, завершение и отмену. Не делайте Despawn/Spawn в TryGetTraversal, SurfaceHeight, DrawFloor или рендере. Если маршрут найден, но проверка/назначение отказали, текущий шаг движения поглощается, чтобы не пройти за край.

В Multiplayer это выполняется на существующем синхронном пути движения, включая simulation-only контроллеры. Предпросмотр движения лишь читает CanStand; он не создаёт Job и не переносит пешку. Удержание WASD не отменяет распознанный Job перехода, обычная явная отмена остаётся доступной. При цепочке нативных playerForced Jobs перехода контроллер продолжает следовать распознанному Job. IsTraversalJob должен точно распознавать только необходимые Jobs и корректно работать после смены Map и загрузки сохранения.

## Работа расширения с несколькими картами

Дополнительные методы `RimVisionView`:

```csharp
float? offset = view.LayerOffset(otherMap);
bool visible = view.TryProject(otherMap, pawn.DrawPos, viewport, out Vector2 point);
GameObject marker = view.CreateLayerObject(otherMap, "My floor marker");
```

Offset –  относительная высота карты от активной. Null означает, что эта карта сейчас не отображается. В Open расширения дополнительные сцены ещё могут быть не готовы; создавайте объекты после появления LayerOffset в Update. `CreateLayerObject` создаёт объект под корнем указанной карты: его localPosition относится к этой карте, и он рисуется в её проходе. Объект принадлежит расширению; ресурсы Mesh/Material/Texture регистрируются через обычный OwnResource. Удаление этажа уничтожает также его объекты; проверяйте Unity-ссылку перед повторным использованием. По умолчанию на следующей карте прежний RimVisionView закрывается; opt-in RetainOnMapTransfer сохраняет его в пределах группы.

Выбор цели через этажи:

```csharp
var state = view.State;
var ray = new Ray(state.CameraPosition, state.CameraRotation * Vector3.forward);
if (view.TryPick(ray, 30f, out RimVisionSpatialHit hit))
{
    Map targetMap = hit.Map;
    Thing target = hit.Thing;
    IntVec3 targetCell = hit.Cell;
}
```

Ray находится в координатах активной карты. Hit.Point возвращается в том же пространстве, а Hit.Cell –  в координатах Hit.Map с Y=0. Thing может быть null для пола/потолка, в том числе непрозрачной границы неразведанной поверхности: такая граница закрывает цели позади, а запрос действия по клетке в тумане будет запрещён. Выбирается ближайшее пересечение среди доступных слоёв, включая поверхности, закрывающие вид. Дистанция ограничена 2048 клетками. Пикер использует прежние модели/маски пешек и габариты остальных объектов; это не точный физический raycast всей геометрии, особенно процедурных крыш и пользовательских лестниц. Не принимайте по его результату решение о попадании/уроне без игровой проверки.

Строительство в FPV и нативное контекстное меню работают с активной картой. В обзорном 3D-режиме доступно прежнее меню строительства: наведение на пол или объект подготовленного видимого слоя выбирает его карту; иначе используется рабочая плоскость активного этажа, в том числе над пустотой для постройки перекрытия. Протягивание закрепляет карту при нажатии, а очередь размещения хранит целевую Map явно и переносится при смене активной пространственной сцены. Условия размещения повторно проверяет native Designator целевого мода; это не мгновенное строительство. Выбор пешки через карточки/NextPawn охватывает CollectMaps и активирует её подготовленную сцену. Ручные обычные пули могут пересекать карты только при явном CanShootAcross; каждая проверяет реальные полы, потолки и цели, а урон выполняется на карте попадания. Это не добавляет автоматический межкарточный AI-бой, межэтажные взрывы или поддержку произвольного стороннего класса снаряда. Прочие межкарточные действия по-прежнему требуют отдельной регистрации и проверки.

## Межкарточные действия

```csharp
IDisposable RimVisionSpatial.RegisterProvider(
    string id, RimVisionSpatialProvider provider, int priority = 0);

IDisposable RimVisionSpatial.RegisterAction(
    string id,
    Func<RimVisionLayerActionContext, AcceptanceReport> validate,
    Func<RimVisionLayerActionContext, bool> execute,
    int priority = 0);

IDisposable RimVisionSpatial.RegisterJobAction(
    string id,
    Func<RimVisionLayerActionContext, AcceptanceReport> validate,
    Func<RimVisionLayerActionContext, Job> createJob,
    int priority = 0);

bool RimVisionSpatial.RequestAction(
    string id, Map targetMap, Thing target, IntVec3 cell, int value = 0);
```

Зарегистрируйте обработчик через `RimVisionSpatial.RegisterAction` либо `RegisterJobAction`. Аргументы: namespaced ID, чистый Validate и Execute либо фабрика нативного Job. Эти регистрации не добавляют строку в обычное меню –  вызывайте из своего HUD/окна:

```csharp
view.RequestLayerAction("author.mod:use", hit.Map, hit.Thing, hit.Cell, value: 0);
```

Либо используйте статический `RimVisionSpatial.RequestAction` для активного вида. Контекст содержит Pawn, SourceMap, TargetMap, Target, Cell и Value. Обе карты должны существовать и принадлежать одной группе провайдера, цель должна находиться на TargetMap, клетка –  в её границах и вне тумана войны. CanInteract провайдера и Validate действия обязаны разрешить операцию. По умолчанию CanInteract запрещён.

Проверяйте дальность в общем пространстве этажей, стены/перекрытия/проёмы, доступность перехода, владение, стоимость и ограничения целевого мода. Используйте операции/Jobs этого мода; при межкарточном Job IsTraversalJob должен разрешать необходимый нативный путь. Ни визуальный Pick, ни факт связи этажей не означают, что персонаж может использовать объект сквозь стену.

В SP запрос проходит общую очередь с обычными API-действиями, сохраняя порядок и проверку пешки. В Multiplayer межкарточный запрос передаётся MP-аддоном RimVision. Сессия владельца и обе карты проверяются при исполнении; затем повторяются CanInteract/Validate и назначается Job либо выполняется операция. Стороннему аддону не нужно вызывать внутренние сетевые команды RimVision. Требуется соответствующая версия MP-аддона на всех клиентах.

Validate/CanInteract/TryGetTraversal/CanStand/IsTraversalJob читают только детерминированное игровое состояние; игровой RNG допустим лишь внутри выполнения нативной операции/Job, а не в проверках. Локальные проверки запроса не создают Job и не меняют мир. Сам провайдер не сохраняется –  сохраняются данные целевого мода и его Job. Новые Scribe-ключи ядра не добавлены.

```csharp
IDisposable WorkMinigames.RegisterForPawn(

    Func<Pawn, float, bool> advanceWork = null,

void WorkMinigames.Register(
    JobDef job, Func<WorkMinigame> create, Func<Pawn, float> remainingTicks = null);

void WorkMinigames.Register(
    JobDef job, Func<WorkMinigame> create, Func<Pawn, float> remainingTicks,
    Func<Pawn, float, bool> advanceWork);
```

| Член WorkMinigame | Назначение |
| --- | --- |
| `Instructions` | Обязательный текст инструкции. |
| `Score` | Обязательный текущий локальный счёт. |
| `Restart()` | Обязательный перезапуск локальной игры. |
| `Update(bool paused)` | Обязательное обновление с учётом паузы. |
| `Draw(Rect rect)` | Обязательная отрисовка интерфейса. |
| `Title` | Заголовок; можно переопределить. |
| `ScoreLabel(int score)` | Форматирование подписи счёта; можно переопределить. |
| `PointsPerReward` | Порог очков для награды; по умолчанию 5. |
| `WindowSize` | Размер содержимого окна; по умолчанию 430×470. |
| `Dispose()` | Освобождение локальных ресурсов игры. |

`WorkMinigames.MinimumSeconds = 5`, `PointsPerReward = 5`, `WorkFractionPerReward = 0.05f` –  публичные базовые параметры. Фактическая выдача проходит существующие настройки, множители и ограничения конкретной работы. `ClampRewardMultiplier(float value)` ограничивает множитель диапазоном 0–5, для NaN/Infinity возвращает 1; вызов не меняет настройки и не выдаёт награду.

Наследуйте `WorkMinigame`, реализуйте `Instructions`, `Score`, `Restart`, `Update(bool paused)`, `Draw(Rect)`; при необходимости переопределите Title, ScoreLabel, PointsPerReward, WindowSize и Dispose. Инициализируйте игру в конструкторе: фабрика должна вернуть готовый экземпляр. При паузе не принимайте игровой ввод и не увеличивайте счёт. Сессия учитывает положительные изменения Score; сброс счёта не отменяет уже выданные награды.

```csharp
WorkMinigames.RegisterForPawn(
    myJobDef,
    pawn => new MyMinigame(pawn),
    remainingTicks: pawn => EstimateRemainingWorkTicks(pawn),
    advanceWork: (pawn, fraction) => AdvanceNativeWork(pawn, fraction));

WorkMinigames.RegisterDefault(WorkMinigameKind.Mining, pawn => new MyMiningGame());
```

Названия MyMinigame/EstimateRemainingWorkTicks/AdvanceNativeWork в этом фрагменте –  ваши реализации. Полный пример без этих заглушек находится в `Example/Source/ExampleMod.cs`.

`RegisterForPawn` имеет приоритет над заменой категории, замена категории –  над встроенной игрой. Оба метода возвращают IDisposable; повторная регистрация требует явного `replace: true`. Снятие замены не восстанавливает предыдущую регистрацию и не пересоздаёт уже открытую игру. Старые `WorkMinigames.Register(JobDef, Func<WorkMinigame>, ...)` сохранены с прежней семантикой замены.

`remainingTicks` необязателен для работ, длительность которых уже умеет определять RimVision. Возвращайте оставшиеся simulation ticks при текущей скорости работы; без оценки нестандартная работа может не открыть миниигру. Существующий порог –  пять секунд, а открытие зависит от настроек, активного ручного задания и текущего toil.

`advanceWork` необязателен для поддерживаемых нативных Jobs. Для нестандартной работы он получает долю операции после применения множителя наград; вызывается на существующей границе WorkMinigameRewards → WorkProgressBonus, в Multiplayer –  синхронно. Его результат true подтверждает награду. Повторяющиеся неподтверждённые награды могут вызывать обработчик снова: возвращайте true только при фактическом прогрессе. Соблюдайте нативные ограничения, пределы оставшейся работы и завершение Job. Прогресс передаётся существующему владельцу работы; не создавайте второй счётчик наград и не меняйте мир из Draw/Update.

Замена категории меняет фабрику игры, сохраняя классификацию и настройки множителя исходной работы. Категории: Snake, Mining, Woodcutting, Research, Building, Repair, Crafting, Sowing, Harvest, Dismantling, Smoothing, Bandaging, Chess, Horseshoes. Локальная миниигра и её визуальный счёт не сохраняются; подтверждённые награды сохраняются существующим компонентом RimVision.

## Multiplayer

API предоставляет путь синхронизации, но не делает произвольный сторонний код автоматически детерминированным. Все участники должны иметь одинаковые версии RimVision, MP-аддона, целевого мода и совместимости, одинаковые регистрации и общие настройки симуляции.

Execute, createJob и advanceWork читают только синхронизированные игровые данные. Не читайте там камеру, Input, Time, локальную миниигру или RimVisionApi.Current. Для игровой случайности используйте штатный RNG в синхронизированном исполнении; для локальных эффектов –  свой System.Random. Не создавайте Unity-ресурсы в игровых обработчиках. Настройки влияния на мир синхронизирует сам аддон либо штатный механизм целевого мода.

API не меняет существующие Scribe-ключи, типы JobDriver и сериализацию команд. Статическая проверка путей выполнения не заменяет проверку конкретного аддона в игре и Multiplayer.

## Границы контракта

Руководство описывает публичные точки расширения, перечисленные выше. Остальные публичные члены внутренних компонентов ядра не становятся самостоятельным контрактом совместимости только из-за своего access modifier.

- Пространственное представление совмещает карты по X/Z с вертикальным смещением. Произвольные поворот, горизонтальный сдвиг, масштаб и объединение симуляций карт не предусмотрены.
- Одновременно отображается до 16 дополнительных карт. Стоимость рендера и памяти растёт с числом карт; прозрачные эффекты между проходами могут требовать отдельного согласования.
- Маски пола/крыши и визуальная высота не создают физику падения, универсальные hitbox или распространение звука. Межкарточные столкновения ручной обычной пули включаются отдельно через CanShootAcross/BlocksProjectile; пикер не является авторитетным источником урона.
- Стандартные локальные команды не перенаправляются на другую карту автоматически. Для неё используется отдельное зарегистрированное действие и повторная игровая проверка.
- По умолчанию нативное управление требует spawned Actor и Carrier на одной карте. Opt-in SupportsContainedActor в API 1.5 разрешает пассажира в настоящем контейнере носителя; произвольный удалённый Actor без этой связи не разрешён.
- Замена атаки передаёт её исполнение провайдеру. Она сама не интегрирует произвольный класс снаряда в стандартный renderer. Поток удержания доступен отдельно через opt-in UsesInputPhases API 1.5. Локальное отображение и дополнительные команды реализуются соответствующими расширениями/действиями.
- Отслеживаемые запросы, native axes и фазы атаки используют отдельные команды обновлённого MP-аддона; прежние command/Scribe форматы сохранены. Синхронизация произвольных локальных полей автоматически не создаётся. Состояние симуляции и сохранения должны иметь одного нативного владельца.

Описание обновлено для исходников API 1.6.0. Выполнен статический разбор непосредственных зависимостей. Для изменения 1.6 сборка, тесты и запуск игры не выполнялись. Документация не подтверждает работоспособность конкретного аддона в игре или Multiplayer.
